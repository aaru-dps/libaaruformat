== 🎮 Nintendo GameCube and Wii Disc Junk Data

This annex describes the junk fill scheme used by Nintendo GameCube (GOD) and Wii (WOD) optical discs, and how AaruFormat detects, strips, and regenerates this data.

=== 📖 Overview

Nintendo GameCube and Wii discs fill unused regions with deterministic pseudorandom data generated by a Lagged Fibonacci Generator (LFG).
This junk data occupies all disc space not used by the file system, including gaps between files, the space after the last file, and inter-partition areas on Wii discs.

Because the junk is algorithmically generated from a small seed, it can be perfectly reconstructed at read time without storing the actual bytes.
AaruFormat exploits this by:

. Detecting junk regions during conversion
. Recording only the LFG seed and region boundaries in a compact junk map
. Marking those sectors as `SectorStatusGenerable` (`0xB`) in the deduplication table, storing no block data
. Regenerating the exact original bytes on read

This eliminates storage of up to 90% of a typical disc's content, since most GameCube and Wii discs contain far more junk than actual game data.

=== 🎲 Lagged Fibonacci Generator (LFG)

==== Algorithm

The PRNG used is a Lagged Fibonacci Generator with the following parameters:

[cols="2,3",options="header"]
|===
|Parameter |Value
|Buffer size (K) |521 words (uint32)
|Second tap (J) |32 words
|Seed size |17 words (uint32)
|Output quantum |K × 4 = 2084 bytes
|Operation |XOR
|===

==== State Initialization

The LFG is initialized from a 17-word (68-byte) seed in big-endian format:

. The 17 seed words are byte-swapped from big-endian to native and placed in buffer positions 0–16.
. Positions 17–520 are filled using the recurrence:
+
[source]
----
buffer[i] = (buffer[i-17] << 23) ^ (buffer[i-16] >> 9) ^ buffer[i-1]
----
. A bit-correction quirk is applied: for each word, bit 18 is shifted instead of bit 16, producing a specific pattern in bits 22–23 that serves as a validity marker.
. All 521 words are byte-swapped back and the buffer is advanced forward 4 iterations.

==== Byte Generation

Output bytes are read sequentially from the 521-word (2084-byte) circular buffer.
When the buffer is exhausted, the forward step generates the next quantum:

[source]
----
Forward step:
  For i in [0, J):      buffer[i] ^= buffer[i + K - J]
  For i in [J, K):      buffer[i] ^= buffer[i - J]
----

==== Seed Extraction (Reverse Engineering)

Given a contiguous chunk of suspected junk data (minimum 2084 bytes, 4-byte aligned), the seed can be recovered by:

. **Validity check**: Verify that bits 22–23 of each byte-swapped word match the expected pattern from the initialization quirk. This quickly rejects non-junk data.

. **Reverse placement**: Place the 521 words into the LFG buffer at the position corresponding to their stream offset (modulo K).

. **Backward steps**: Undo forward iterations to recover the state at initialization time:
+
[source]
----
Backward step (reverse of forward):
  For i in (K, J]:      buffer[i-1] ^= buffer[i-1-J]
  For i in (J, 0]:      buffer[i-1] ^= buffer[i-1+K-J]
----

. **Reinitialize**: Verify the recurrence relation against the recovered buffer. If all 521 values match, extract the first 17 words as the seed.

. **Validate**: Re-initialize the LFG from the extracted seed, advance to the original stream position, and confirm the output matches the input data byte-for-byte. The number of consecutively matching bytes is returned.

=== 📀 Disc Structure

==== GameCube

GameCube discs are unencrypted. The disc layout is:

[source]
----
0x000000 – 0x000440: Disc header (1088 bytes)
0x000440 – variable: Boot block, apploader, DOL executable, FST
variable – end:      File data + junk fill
----

Junk detection operates on aligned 0x8000-byte (32 KiB) blocks:

* **System area** (header through FST) is always treated as data.
* **File regions** are identified from the File System Table (FST).
* Everything else is candidate junk.

==== Wii

Wii discs add encryption and partitioning:

[source]
----
0x000000 – 0x040000: Unencrypted disc header and partition table
0x040000 – end:      Partitions (each encrypted with a per-partition AES-128 key)
                     + inter-partition junk (unencrypted LFG fill)
----

Each partition consists of 0x8000-byte encrypted groups:

[cols="2,2,5",options="header"]
|===
|Component |Size |Description
|Hash block |0x0400 (1 KiB) |SHA-1 hashes for integrity verification
|User data |0x7C00 (31 KiB) |Actual filesystem data or junk
|===

For Wii, junk detection occurs on the *decrypted* user data within each group, after partition decryption.
Junk in *inter-partition* areas (between partition boundaries) is unencrypted and detected directly.

=== 🔍 Junk Detection (Write Path)

The conversion tool processes the disc in 0x8000-byte blocks and classifies each sector (2048 bytes) as either data or junk.

==== Full-Block Detection

. Read an aligned 0x8000-byte block (16 sectors).
. Attempt LFG seed extraction on the entire block.
. If `ngc_lfg_get_seed()` returns a match covering the full block, the block's PRNG pattern is confirmed.
. For each of the 16 sectors in the block:
** If the sector falls within a known data region (system area or FST file extent): mark as `SectorStatusDumped`, store normally.
** Otherwise: mark as `SectorStatusGenerable`, record the seed in the junk collector, store no block data.

==== Mixed-Block Detection

If full-block detection fails (the block contains a mix of data and junk):

. Identify contiguous runs of non-data sectors within the block.
. For each run of non-data sectors:
.. Attempt LFG seed extraction on the run, passing the run's byte offset within the block for correct alignment.
.. If successful, verify each sector in the run against the seed by advancing the LFG stream to the correct position and comparing output.
.. Matching sectors are marked `SectorStatusGenerable` with the run's seed.
.. Non-matching sectors are kept as data.

==== Junk Collector Merging

The junk collector maintains a sorted list of (offset, length, partition_index, seed) entries.
Adjacent junk regions with the same seed and partition index are merged into a single entry, keeping the map compact.

=== 🗺️ Junk Map (Media Tag)

The junk map is stored as media tag `kMediaTagNgcwJunkMap` (value 84) with the following serialization format (all little-endian):

==== Header

[cols="2,2,2,6",options="header"]
|===
|Offset |Type |Size |Description
|0 |uint16_t LE |2 bytes |Version (currently 1)
|2 |uint32_t LE |4 bytes |Entry count
|6 |uint16_t LE |2 bytes |Seed size in uint32 words (17)
|===

==== Entries (repeated)

Each entry is 86 bytes (when seed_size = 17):

[cols="2,2,2,6",options="header"]
|===
|Offset |Type |Size |Description
|0 |uint64_t LE |8 bytes |Disc byte offset where junk starts
|8 |uint64_t LE |8 bytes |Length of junk region in bytes
|16 |uint16_t LE |2 bytes |Partition index (`0xFFFF` for GameCube or inter-partition Wii junk)
|18 |uint32_t[] |68 bytes |LFG seed (17 words, stored as big-endian uint32 values)
|===

=== 🔄 Junk Regeneration (Read Path)

When a sector marked `SectorStatusGenerable` is read:

. **Lazy initialization**: On first access, the junk map is deserialized from the `kMediaTagNgcwJunkMap` media tag.

. **Lookup**: A binary search on the sorted junk entries locates the entry covering the requested disc offset.

. **Stream positioning**: The LFG is initialized from the entry's seed. The PRNG state corresponds to the beginning of the 0x8000-aligned block containing the entry. The LFG is advanced (by discarding bytes) to the exact position of the requested sector within the stream.

. **Generation**: The requested number of bytes (typically 2048) are generated from the LFG and returned to the caller.

==== GameCube (GOD)

For GameCube discs, regenerated junk is returned directly. The sector status is reported as `SectorStatusDumped` to the caller, since the data is complete and correct.

==== Wii (WOD)

For Wii discs, regenerated junk requires additional processing because Wii sectors are encrypted:

. The junk for all 16 sectors in the physical 0x8000-byte group is regenerated or read from storage.
. Junk is placed into the user data area (0x7C00 bytes) of the group alongside any real data sectors.
. The complete group (hash block + user data) is re-encrypted using the partition's AES-128 key via `wii_encrypt_group()`.
. The caller receives the encrypted sector slice, byte-identical to the original disc.

A group cache prevents redundant re-encryption when multiple sectors from the same group are read sequentially.
A recursion guard flag (`wii_building_crypto_block`) prevents infinite loops when the library reads sibling sectors from the same group during assembly.

=== 📊 Storage Savings

A typical Nintendo GameCube disc is 1.4 GiB, of which many games use only 100–500 MiB of actual data.
The remainder is LFG junk.
By storing only the junk map (typically a few kilobytes) instead of hundreds of megabytes of pseudorandom bytes:

* **Deduplication**: Zero junk sectors stored in data blocks — no hash table entries, no block allocation.
* **Compression**: Even without deduplication, LZMA/Zstandard cannot compress pseudorandom data. Removing it before compression prevents wasted CPU cycles on incompressible blocks.
* **Typical reduction**: A 1.4 GiB GameCube image may compress to 200–500 MiB. A 4.7 GiB (single-layer) or 8.5 GiB (dual-layer) Wii image achieves similar proportional savings.

=== ⚠️ Limitations and Edge Cases

* **Minimum seed extraction size**: The LFG requires at least 2084 contiguous bytes (521 × 4) of PRNG output to extract a seed. Very short junk regions cannot be detected and are stored as regular data.

* **4-byte alignment**: Seed extraction requires the data buffer to be aligned on a 4-byte boundary relative to the LFG stream position. Misaligned data will fail seed extraction.

* **Wii group granularity**: On Wii discs, junk within encrypted partitions is detected at the group level after decryption. The junk map records byte offsets within the decrypted user data area, not the encrypted group.

* **Non-standard junk patterns**: Homebrew or modified discs may use non-standard fill patterns. The LFG validity check (bits 22–23 pattern) rejects these quickly, and they are stored as normal data.
