=== 👯 Twin Sector Table (`TWTB`)

Some media carry more than one physical sector answering to the same sector address.
Floppies with duplicated sector IDs used for copy protection, or Compact Discs where the same MSF address is mastered more than once (usually with a different header or Q subchannel), are typical examples.
Such sectors are referred to as “twin sectors,” although the grouping may consist of more than two instances.

Every instance is a full physical sector.
When the medium stores sectors decomposed in several parts (user data, Compact Disc prefix and suffix, MODE 2 subheader, subchannel, DVD and Blu-ray long sector fields, Apple and Priam tags), every instance has its own copy of each part.

==== Storage Model

* *Twin #0* is stored exactly like any other sector: user data in data blocks referenced by the user data deduplication table, prefix and suffix in their own deduplication tables and data blocks, and tags in their per-sector data blocks.
Its entry in the user data deduplication table has the status `Twin` (`0x7`), but its pointer still references twin #0's user data.
Readers that do not understand twin sectors therefore read twin #0 transparently.
* The real status of twin #0's user data is stored in the twin sector table.
* *Twins #1 to n-1* are records of the twin sector table:
** User data is stored in ordinary data blocks, and referenced with a pointer encoded exactly as an entry of the user data deduplication table.
** Compact Disc prefix and suffix use the same data blocks as twin #0, and are encoded exactly as entries of the prefix and suffix deduplication tables.
A twin whose prefix or suffix can be regenerated takes no space besides its entry.
** Small fixed-size tags are stored inside the record.

There is at most one twin sector table per image, indexed with block type `TWTB` and data type `UserData`.

When an image contains a twin sector table, bit 1 (`AARU_FEATURE_ROCOMPAT_TWIN_SECTORS`) of `featureCompatibleRo` is set.
Readers that do not understand it can read the image (getting twin #0 of every twinned sector), but must not modify it, as they would drop the table and leave its entries in the prefix and suffix data blocks unreferenced.

==== Payload

The decompressed payload is made of the component descriptors, followed by the groups, followed by the twin records, with no padding between them.

===== Component descriptors

Each descriptor declares a component present in every twin record, in the order it appears in the record.

[source,c]
typedef struct TwinComponentDescriptor
{
    uint16_t dataType;  ///< Data type of the component.

    uint8_t  reserved;  ///< Reserved, must be 0.

Writers only declare the components that at least one record uses.
Readers ignore descriptors whose data type they do not know, so new components can be added without breaking them.

===== Groups

One group per twinned sector, sorted by `sector` in ascending order, without duplicates.

[source,c]
typedef struct TwinSectorGroup
{
    uint64_t sector;       ///< Sector index as used in the deduplication tables.
    uint32_t first;        ///< Index of the record of twin #1.
    uint16_t count;        ///< Instances, including twin #0, at least 2.
    uint8_t  twin0Status;  ///< Status of twin #0's user data.
    uint8_t  reserved;     ///< Reserved, must be 0.
} TwinSectorGroup;

`sector` is the position of the sector in the deduplication tables, that is, with negative sectors already accounted for.
Twins #1 to `count - 1` are the records `first` to `first + count - 2`.

===== Twin records

Each record is `recordSize` bytes:

[cols="2,2,6",options="header"]
|===
|Offset
|Size
|Contents

|0
|4
|Bitmask of present components: bit _i_ set means component _i_, in descriptor order, holds a value for this twin.

|4
|4
|Reserved, must be 0.

|8
|...
|Each component in descriptor order, with the size of its descriptor, followed by zero padding up to `recordSize`.
|===

A component whose bit is not set was not captured for that twin and reads as empty.

==== Consistency Rules

* A sector has a group if, and only if, its entry in the user data deduplication table has the status `Twin`.
* The user data pointer of the deduplication table entry references twin #0's user data.
* Prefix and suffix entries of the records with status `Errored` reference entries within the prefix and suffix data blocks.
* Instances of a twinned sector may have different user data sizes; each pointer references a data block with its own sector size.

==== Example

A Compact Disc where LBA 12345 was mastered twice, with a second copy whose header and Q subchannel differ:

* The user data deduplication table entry of LBA 12345 has status `Twin`, and points to twin #0's 2048 bytes.
* The prefix and suffix deduplication tables hold twin #0's prefix and suffix as usual.
* The twin sector table declares `UserData`, `CdSectorPrefix`, `CdSectorSuffix` and `CdSubchannel`, making each record 8 + 8 + 8 + 8 + 96 = 128 bytes.
* Its group is `{sector = 12345 + negative, first = 0, count = 2, twin0Status = Mode1Correct}`.
* The record of twin #1 holds the pointer to its own 2048 bytes, a prefix entry with status `Errored` and the index of its 16 bytes in the prefix data block, a suffix entry with status `Mode1Correct`, and its 96 bytes of subchannel.
